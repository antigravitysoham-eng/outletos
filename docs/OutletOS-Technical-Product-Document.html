How OutletOS works

The architecture, data flows, user flows, security model and interfaces of a centralized operations platform for restaurant groups — written for the engineers, integrators and reviewers who need to trust it before it runs a kitchen.

Version 1.0Rendered 2026-11-19Sections 19Diagrams 16

OutletOS connects to the POS, delivery apps, kitchen screens, attendance devices, cameras and sensors a restaurant group already owns, and turns them into one live screen per role — sales and costs for owners, station tickets for cooks, regulars and allergies for hosts — with access enforced on the server for every request and every live update. A team of AI agents answers questions over the same permission-checked data.

Overview

OutletOS is a centralized operations platform for restaurant groups. It pulls sales, kitchen, staffing, camera, sensor and guest data from the systems a restaurant already runs, then turns it into one live, role-aware screen for everyone from the owner to a line cook.

Design principles

PrincipleHow it holds
Works with any vendorOne canonical event model. Every source is mapped into it by REST, a no-code webhook mapping or CSV, so there is no POS or hardware lock-in.
LightweightOne Node process, the SQLite engine built into Node, and two production server dependencies (express, plus the Anthropic SDK used only when an API key is set). Runs on a laptop or a small VM.
Real-time by defaultEvery write publishes an event; dashboards update over Server-Sent Events within seconds.
Secure by constructionRBAC and ABAC are evaluated on the server for every request and every live event. Hidden fields are never computed, let alone sent.
Privacy-first visionVideo is processed on-premise; only structured events leave the restaurant. Guest face matching requires explicit consent.
Agents inherit accessAI agents read only through permission-checked tools that run as the signed-in user, and every action waits for human approval.
Demo equals productionThe simulator writes through the same ingest functions as real integrations, so what a prospect sees is what the code does.

Architecture

A single server process hosts the ingest API, the rules, the event store, the live event bus, the policy engine and the read models. The React client is served from the same process.

AI agents

OutletOS includes a team of AI agents. Maître, the orchestrator, takes a question in plain English, delegates it to the right specialist agents (one per module), and merges their reports into one short answer with the figures behind it. Specialists also run a proactive scan every minute, which feeds the live briefing.

Request flow

Question typeWhat Maître does
One domain · “Which station is slowest?”Delegates to one specialist and returns its answer.
Several domains · “Sales and staffing?”Delegates in parallel, then leads with a one-line synthesis.
Root cause · “Why is Restaurant 4 behind?”Finds the branch (or the weakest one), asks the owning specialist, then has every other specialist scan that branch for contributing factors.
Briefing · “What needs my attention?”Runs every available specialist’s scan and ranks findings high → medium → info.
Action · “Acknowledge the speed alerts”Incident Manager proposes the action; the browser shows an approval card; only the user’s click calls the normal acknowledge endpoint.

Guardrails

RiskControl
Agent sees too muchSpecialists only receive tools whose permission the user holds; every tool runs with the user’s principal through scopeBranches, station and department filters and field masking.
Agent changes dataAll data tools are read-only. The one action tool only proposes; the user approves in the UI and the existing POST /api/alerts/:id/ack route re-checks permission.
Prompt injectionReview text and other ingested strings reach the model only inside tool results, which the system prompt treats as data. No tool can send messages, call URLs or write records.
Made-up numbersPrompts require every figure to come from a tool result with its baseline; the local engine composes answers only from tool output.
Out-of-scope questionsQuestions about another branch or a hidden domain get an explicit “not available to your role” answer, never a guess.
AccountabilityEvery run is stored in agent_runs: user, role, question, agents, tools, engine, duration, success. Owners and IT see all runs; others see their own.

Vision & edge

Cameras are the richest and cheapest sensor in a restaurant, but only if video is turned into a few structured events inside the building. OutletOS reuses the existing CCTV, runs small open-licence models on a low-cost edge box, and sends only JSON.

What CCTV can measure

Reliability depends on pixels on the target. A 1080p camera 4 m away gives about 200 px/m, but a nano detector sees the frame at 384–640 px, which leaves about 40–65 px/m. At that density a gloved hand is about 6×13 px, a head covering about 11 px, and use-by text under 1 px. Reliable small-object detection needs about 32 px, and OCR needs 10–20 px per character. So every check sits in one of four tiers (VISION_CHECKS.tier in ingest.js, evidence in docs/research/cctv-metrics.md):

TierChecksBehaviour
Real-timeStation staffed (coverage %), after-hours cold-store entry, walk-in door > 3 min, unattended counter, queue wait (Little’s law), dishes waiting at the pass, zone occupancy, camera healthAlerts on repetition. Counted in camera compliance.
KPITime to first staff approach (proximity, not a “greeting”), first table visit, uniform %Reported as aggregates (p50/p90, %). Alerts only once vision_validated is set for the site.
AuditHair covering, gloves, phone use (aggregate, opt-in), sink visit after raw handlingSent to a supervisor review queue. Never alerted automatically, never ranked per person. Real-time only where a camera passes the pixel-density test (≥ 125 px/m at the head, ≥ 250 px/m at the hands).
DroppedUse-by label OCR, clear-liquid spillsAccepted on the API for compatibility, never scored. Labels move to a scan workflow; spills need thermal cameras or manual checks.

Validation before alerts go live: each site runs in shadow mode for two weeks. Ground truth is sampled by camera × daypart × lighting. Real-time alerts must reach ≥ 90% precision and ≥ 80% recall; KPIs must be within 5% daily error. Drift is audited monthly with 50 snapshots per camera.

Privacy: staff metrics stay at station or shift level, in line with the DPDP Act, GDPR and the EU AI Act.

Operations back office

OutletOS runs the restaurant as well as watching it. The back office covers the same ground as India's leading restaurant POS (Petpooja) and its competitors, and every sensitive action feeds the same audit trail, reports and AI agents. The full feature gap analysis is in docs/research/petpooja-gap.md.

Point of sale

CapabilityHow it works
Tables & areasAreas such as AC hall, family and terrace, each with its own numbered tables. Each table shows a live status: free, reserved, ordering, running or billed, plus elapsed time and running total. Takeaway and delivery orders sit alongside tables.
KOTOnly new quantities are fired, routed by station (Tandoor, Curry, Bar…) and shown on the kitchen display. Cooks bump a ticket to mark it ready. Cancelling an item after its KOT requires a reason and is logged.
Discounts & NCPreset percentages with a required reason. Discounts above 25% and complimentary (NC) bills need a manager. All are logged to audit_log.
Bill & tenderTax invoice with GSTIN, FSSAI number, SAC 9963 and a CGST/SGST split for India. Totals round to the rupee. Bills are numbered per financial year (R1/26-27/000001). Split tender across UPI, card, cash, wallet and credit. Reprints and edits made after printing are logged.
SettlementWrites a canonical order through recordOrder (net + tax), so the POS feeds sales, GST, day end, reports and agents exactly like any external POS.

Inventory & menu

CapabilityHow it works
Recipes (BOM)Each dish has a per-portion bill of materials. Quantities are scaled so the recipe cost equals the dish's standard cost, which keeps theoretical food cost consistent with sales.
Theoretical stockOn hand = last physical count + purchases − wastage − Σ(items sold × recipe qty) since the count. It is computed in SQL on request, so it never drifts.
ReorderAverage daily usage over 14 days. Reorder point = usage × (vendor lead time + 1). Par = usage × (lead time + 2). Suggested POs are grouped by vendor.
PurchasingRaise a PO, then receive it (GRN), which adds a purchase stock move.
Wastage & countsWastage is logged with a reason. Each physical count records the variance between actual and theoretical stock: shortage value by ingredient points to theft, over-portioning or unrecorded waste.
Menu & 86Group-wide prices with a margin guard (a price must clear food cost × 1.25). Availability (86) is set per branch and respected by the POS and by simulated delivery orders.

Reservations

Bookings from phone, walk-in and dining platforms, with deposits, notes and no-show tracking. A waitlist covers walk-ins. Seating a booking assigns a table and opens the order on the POS. Each booking is linked to a guest profile by phone.

Finance & compliance

CapabilityHow it works
Day endFor each branch and business date it summarises net sales, tax and its split, tender mix, channels, discounts, NC, cancellations, reprints and wastage. The day closes with a declared cash amount, and the variance is stored. Closing is refused while tables are still open.
Tax registerTaxable value, CGST/SGST (or VAT) and invoice value by branch and day, showing GSTIN and state. It feeds GSTR-1 (B2C) and GSTR-3B.
Tally XMLOne sales voucher per branch per day, loaded via Import Data → Vouchers. Ledgers: Sales - Restaurant, Output CGST / SGST, UPI / Card / Cash collections, Aggregator Receivable, Round Off.
Aggregator reconciliationExpected payout per order = gross − commission − 18% GST on commission − 0.5% TCS. Orders missing from the payout or short-paid are listed for dispute. In the demo, payout lines are simulated deterministically.
Leakage & staff riskSensitive actions per 100 bills and as a percentage of sales, by branch. Each staff member gets a risk score: a z-score against peers of cancels, edits after print, reprints and discount value. It is a prompt to review CCTV and bills, not proof.

Reporting & forecasting

Reports & Analytics is one management report per period: today, yesterday, 7 days or 14 days. Each period is compared with the prior equivalent; today is compared with the same time last week. The report reads the same fact tables as the dashboard. Closed days come from a cached daily rollup, so only today is recomputed on each request; a 14-day report takes about 0.5 seconds. Fields a role may not see are never computed. The report exports to CSV and prints to an A4 PDF.

Comparisons

The comparisons are:

  • Branch league table: ranked by share of KPIs on target, then by sales, with cells coloured against each target.
  • Daily or hourly sales against the prior period and budget.
  • Channel mix and dayparts, compared with the prior period.
  • Menu engineering (Kasavana–Smith): each item is classed as Star, Plowhorse, Puzzle or Dog by menu mix (against 70% of fair share) and by contribution margin (against the weighted average).

Forecasting

Method:

  • Holt's linear trend is fitted to weekday-adjusted daily sales over 28 days. Weekday indices come from each day's ratio to its own week.
  • The 80% prediction interval comes from recent one-step errors and widens with the horizon.
  • Today's close = actual so far + forecast × (1 − usual share of the day already done). The chance of hitting budget comes from the same error model.

Outputs: the 7-day plan converts forecast orders into labour hours needed at the TPPH target and compares them with rostered hours, and converts forecast sales into a food purchase at trailing food cost.

Accuracy: every report backtests last week from the weeks before it and shows the MAPE and interval coverage. On the demo data the MAPE is about 5%.

Webhook security & devices

Webhooks: where the vendor signs payloads (Square, Uber Eats, Razorpay), OutletOS checks the HMAC over the raw body using the configured secret. Unsigned or wrongly signed calls get a 401 and the connector records the error. Secrets are stored server-side and only ever returned masked.

Devices: ADMS accepts only device serial numbers registered on an eSSL or ZKTeco connector. It maps each device PIN to the staff employee code.

Starter mappings deliberately use generic paths. Always confirm them against a real vendor payload before going live.

Telegram assistant

A Telegram bot is a second front door to the same server (server/src/telegram.js). It holds no data of its own and makes no access decisions of its own:

  • Linking: a user requests a single-use code (8 characters, 10-minute expiry) and sends /start CODE. The chat id is then bound to that user in telegram_links.
  • Authorisation per message: each update re-loads the user (inactive users are unlinked) and builds the same principal as a web session. Commands call the agent tools (runTool), which enforce the permission and branch scope; free text goes to runChat, the same orchestrator as Ask Maître.
  • Approvals: acknowledgements are proposed as inline buttons bound to the chat and user, expire after 30 minutes, and re-check alerts.ack and alertAllowed before writing.
  • Push: a bus subscriber sends high-severity alerts to linked users for whom eventVisible and alertAllowed hold, capped at 12 per chat per hour.
  • Transport: long polling (outbound only) or webhook at /api/telegram/webhook/:secret with Telegram's secret-token header; both secrets are compared in constant time. Group chats are refused; 20 messages per minute per chat.

What launch creates

POST /api/setup/complete runs in a single transaction and creates:

  • outlets, with type, hours and a legal profile
  • dining tables per area
  • menu items
  • a roster per outlet, scaled by seats, with local loaded wages
  • user accounts with temporary passwords, shown once
  • cameras and sensors for the enabled Vision and Food safety modules
  • connectors awaiting credentials
  • organisation settings, modules, targets and setup status

It then optionally builds four weeks of sample activity for exactly these outlets, menu and team. The navigation shows only enabled modules.

Front-end performance

  • Code splitting: each page is a separate chunk loaded on demand and prefetched when the browser is idle. The first load ships only the app shell: 297 KB (95 KB gzipped) instead of 1.96 MB.
  • One live connection per browser: browsers allow six HTTP/1.1 connections per host across all tabs, so one Server-Sent Events stream per tab starved page loads once several tabs were open. One tab now wins a Web Lock and holds the only stream; it relays events and connection status to the other tabs over a BroadcastChannel scoped to the session. When that tab closes, another takes over automatically. Behind an HTTP/2 proxy the limit disappears, but the sharing still saves server connections.
  • Motion: sidebar width, group expand/collapse and the phone drawer animate with one easing curve; all motion is disabled for users who set "reduce motion".

Privacy & compliance

Built in

Video stays on-premise. Only structured events leave the restaurant.

Face matching is opt-in. The API rejects method: face for any guest without consent_face.

Least privilege. Phone numbers are masked, pay rates hidden and branches scoped by default.

Tamper-evident HACCP. Readings are timestamped by the server and never edited.
